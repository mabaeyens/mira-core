01 · The mechanism

One draft, one verify, keep the prefix

Speculative decoding buys speed by guessing several tokens cheaply, then checking them all in a single expensive pass. The trick only works because on this hardware, checking four tokens costs almost exactly what checking one does.

The classic setup (Leviathan et al., 2211.17192) uses a small draft model beside a big one. Self-speculative decoding drops the second model: a lightweight MTP head bolted onto the backbone does the drafting, in the DeepSeek-V3 style. The head predicts token t+1 from the backbone's own hidden state, then chains: each draft feeds the next.

Core idea
A cycle is only worth running if the backbone forward over 4 tokens costs about the same as over 1. That flatness is the entire economy of speculative decoding.
Mechanism
The backbone runs once per cycle in verify mode with n_confirmed=1. Correctness never depends on the draft being right: every emitted token is argmax(full-vocab verify), so a bad guess costs throughput, never quality.
Measured

02 · The free lunch and its price

Free-M verify, and the MoE tax on it

The dense matmuls that dominate a forward pass are memory-bandwidth bound at decode. Widening the batch from 1 to 4 tokens rides the same weight read, so it is nearly free. The mixture-of-experts routing is the one part that is not.

Start here · what “free-M” and a cycle actually are

M is the verify width — the number of token positions the big model scores in a single forward pass. “Free-M” is the name for the finding this section proves: going from M=1 to M=4 costs almost nothing extra, because a decode pass is bottlenecked on reading the weights out of memory, not on the arithmetic. Four tokens ride the same weight read, so checking four is nearly as cheap as checking one. That flatness is the entire reason speculative decoding pays.

A cycle is the repeating unit drawn in section 01. Broken down by step it is three moves:

1 · draft
the lightweight MTP head cheaply guesses the next few tokens, each guess feeding the next (d1→d2→d3).
2 · verify
one backbone forward scores all of them at once — this is the pass whose width is M.
3 · emit
keep the longest run of guesses the backbone agrees with, add its own token as one free correction at the first miss, then start the next cycle.

Broken down by time, that same cycle is a wall-clock budget: the stacked bar at the foot of this section shows one cycle is about 34 ms, of which verify is 77%, drafting is 21%, and host bookkeeping is the rest. So “step” tells you what happens; “time” tells you where the milliseconds go — and the winning lever in section 05 attacks that 21% draft slice.

03 · The substrate

A hybrid, mixture-of-experts backbone

The model shapes every decision below. It is a mixture-of-experts and a hybrid-attention stack, and both facts are why the usual speculative-decoding playbook does not transfer wholesale.

Core idea
Everything downstream is shaped by two facts: routing cost scales with the chain (section 02), and linear-layer state does not branch (section 06).
The numbers that matter
256 experts, 8 active per token. Hidden 2048, vocab 248320, head_dim 256. 4-bit weights at group size 64. The 248320 vocab is the specific number the winning lever exploits.
Measured

04 · How deep to draft

A controller that prices each depth

Drafting deeper wins more tokens per cycle only until the added draft cost and falling accept rate stop paying. A per-sequence controller finds that peak instead of guessing it.

It maximizes score(d) = E[tokens](d) / time(d), using an EMA of the conditional accept rate at each depth and the measured per-depth cost. Depth 0 is a park (decode normally, no speculation); a global hand-back drops the whole sequence to stock decode when MTP is a net loss. This objective subsumes the published heuristics (SpecDec++, DISCO, llama.cpp's p_min): they all approximate the same expected-tokens-per-unit-time argmax.

05 · The winning lever

Draft a narrower vocabulary

The draft head spends most of its time projecting a hidden state onto all 248,320 vocabulary rows, only to take one argmax. Project onto the first N rows instead and the draft gets cheaper with no change to what gets emitted.

This is safe by construction. The full-vocab backbone verify still decides every token, so a narrower draft vocabulary can only ever cost accept rate, if a true next token's id happens to land beyond N. It can never change the output. Qwen3's byte-level merges put common tokens at low ids, so a generous N covers essentially everything the model generates.

Reminder · vocabulary, token ids, and the knee
the vocabulary
the fixed list of 248,320 tokens (word-pieces) the model can ever output. Every step it produces one score per row and takes the highest — that pick is the next token. The lm_head is the big matrix that turns a hidden state into those 248,320 scores.
token ids
just the row numbers, 0 to 248,319. Qwen3's tokenizer gives low ids to the most common pieces (frequent words, punctuation, code symbols) and high ids to rare ones. So “the first N rows” means “the N most common tokens.”
the knee
as you shrink the draft's vocabulary N, speed climbs while accept rate holds — up to the point where accept starts to fall. That elbow in the curve is the knee. 131072 sits right on it: half the width, zero accept loss.
past the knee
cut further (e.g. 32768) and you've trimmed so hard that real next-tokens start landing beyond N. Accept collapses, the controller starts parking, and you lose more than the narrower projection saved.
Core idea
Make the draft cheaper without making it dumber. Cost lever, not an accept lever, so it sidesteps the wall in section 07 entirely.
Mechanism
A one-line change at the two draft call sites: mtp_forward(…, draft_vocab=N), plus the penalty-context filter. Verify untouched. Off by default (draft_vocab=0) reproduces the old path byte-for-byte.
Measured
at N=131072: 71.2 → 76.0 t/s (+6.7%), accept 0.857 → 0.857 (zero loss) → omlx parity reached

The increment that did not stack: depth 4

Cheaper drafts should make deeper chains affordable, so raising max_draft to 4 looked like a free stack on top. It is not. Measured, it lowers throughput: the controller only picks depth 4 for 125 of 1458 cycles and depth 5 for 15, and the added draft cost plus the extra expert union (section 02) outweigh the rare deep hit. This is the falling right shoulder of the score hump, measured rather than argued.

The increment that vindicated the mechanism but stayed marginal: frequency-remap

The reduced-vocab lever leans on an assumption: the model's hot tokens sit at low ids. They mostly do, thanks to Qwen3's byte-level merges, but not perfectly. So the natural refinement is to stop projecting the first N rows and instead project the N most-frequently-emitted rows, mapped back through an id table. Same projection cost as a contiguous slice, but every column is now a token the model actually uses, so a narrow N should hold the accept rate that the contiguous slice only keeps at a much wider 131072. This is FastMTP's vocab-compression idea (2509.18362) applied to the draft head.

The first map was built from Mira's chat history, and it refuted itself. It scored beautifully on the corpus it was trained on and came apart on held-out prompts, roughly 9% of true tokens uncovered: textbook train-on-test. The fix was a broader map, built from chat plus the model's own eval generations (13,712 distinct emitted ids) and held out from the bench prompts. On that map the mechanism is genuinely real.

But vindicating the mechanism is not the same as banking speed. The already-shipped first-131072 slice is also a wide, cheap draft with near-full accept. Measured head to head, remap's net gain over it is about 1% in decode throughput, well inside the thermal noise of a session this hot, and it costs a drift-prone map file plus id-translation on the hot path every cycle. The honest disposition: the mechanism is proven, the increment is real but marginal. The banked lever stays first-131072; remap is kept gated behind an env flag and documented, not switched on.

07 · The lever that is spent

The accept wall

The other way to go faster is to make the head guess better, so more drafts survive. We already ran that experiment to its end, and it hit a capacity ceiling.

We built the FastMTP recipe (2509.18362) twice: a single-step self-distilled head fine-tune, and a multi-step recursive version that carries the head's own hidden state forward, which is the HASS exposure-bias fix (2408.15766). On the fixed dense head the ceiling was hard: +2 points at depth 3 only, with depth 1 and 2 immovable. A stronger head plateauing is what makes retraining the weaker MoE head low expected value. So we pivoted from the accept lever to the cost lever in section 05, and it worked.

The MoE-specific accept ideas in the literature do not rescue it either, for reasons specific to a resident 32GB deployment:

08 · A subtle claim, stated precisely

Lossless is not byte-identical

Every emitted token is the backbone's own greedy pick, yet the text is not bit-for-bit identical across draft settings. Both statements are true, and the gap between them is where a careless claim gets made.

Two words this section leans on
greedy
the decoding rule where each step always takes the single highest-scoring token — no sampling, no temperature, no randomness. Same input plus same numerics gives the same choice. These benchmarks all run greedy.
lossless
the speculative machinery never changes which token greedy would have picked: every emitted token is still argmax(full-vocab verify), the backbone's own choice. What it does not promise is identical bytes — see below.

So “lossless” here means same decision rule, same quality, not same output text. The bytes can still shift because the tie-breaking arithmetic differs by batch width on this hardware.

The invariant emit = argmax(full-vocab verify) holds by construction. But changing the draft changes which batch widths the verify runs at, and on M5 the batched attention numerics (mlx#3897, mlx#3860, both closed won't-fix, so we always run MLX_ENABLE_TF32=0) resolve argmax ties slightly differently at different widths. That is the same non-determinism that already makes batch-1 and batch-4 diverge in production. We verified by reading divergent outputs side by side that they are equal quality, not regressions.

The audit: where the last few t/s hide

Chasing 80 harder, I put the engine and the literature through a twelve-way audit and turned two of the reviewers loose on this very page. The blunt result: the 76.0 base is softer than it looks. It is the top of a noisy pass-pair whose low end is 70.7, and every number here was measured at short context while production serves 131072. I later profiled that taper: decode falls from 73 t/s at 2k to 25 at 32k to 11 at 64k as the KV read takes over, so the 76 base is a 2k number and the served regime is 7×+ slower — “80” describes a benchmark, not the product. So the honest reading is that 80 is an aspiration, not a delivery — but the audit turned up more than trims. The first card below is the surprise: the verify batch never coalesces its expert gather because MLX gates the sort at a width the single-stream batch never reaches, and flipping it on is bit-identical and cut ~20% off every MoE forward in a resident A/B that held steady across 32 cold layers — a one-time jump that the resident full-model A/B then measured at +4.6% end-to-end: real, lossless, and dead-consistent, but a third of the projection, so it lifts 76 to ~79.5 without clearing 80. The one lever with compounding headroom is still retraining the MoE head, ruled out so far only on the dense one: a faster head lifts accept, which multiplies every cycle after. Both are unrun. Before I am allowed to write “exhausted”, they have to be.

Bounded penalty context

Every cycle marshals the full token history to replay the repetition penalty, but the penalty only reads the last 64 tokens. A host-only probe measured the waste: 3.3 ms/cycle at 64k context, and bounding it to the window is byte-identical. That is ~10% decode at 64k (2–5% at 16–32k), paid only at long context — exactly the served regime every headline skipped.

measured · promising~10% @64klossless

Expert-gather coalescing — measured

MLX sorts the MoE expert gather only at ≥64 routed indices; a single-stream verify batch routes 4×8=32, so it runs unsorted and an expert two verified tokens share is read twice. I measured the overlap live: 20.6 distinct of 32 (~36% reuse). Forcing the sort on is bit-identical (|Δ| = 0) and the win scales with reuse — the coalescing signature. A resident A/B then streamed the verify forward through 8–32 distinct cold layers (a 14 GB working set, cache-defeating) and the speedup held rock-steady at on/off 0.80 — ~20% off every MoE forward, not decaying with scale. Those forwards are 55% of the cycle, so it projected to +12% end-to-end. The resident full-model A/B then settled it: 36 paired-interleaved reps with the model fully resident gave +4.6% end-to-end, 76 → ~79.5 — ON faster in 36/36 pairs, byte-identical output, accept unchanged. Real and free, but a third of the projection: MoE is a smaller share of the cycle than 55% once the whole stack is resident, so this trims rather than clears 80. The fix is a threshold, not a kernel: sort at ≥16 (catches verify M=2–7, spares single-token decode), via Mira's own MTP patch.

N-gram draft extension

After the head's drafts, scan the context for the current suffix and append the following tokens into the same verify. Free draft tokens, no head forward, and it stays a linear chain, so the GatedDeltaNet recurrence never forks — the exact blocker that killed the tree. Large on code and edits, ~0 on prose. Untried.

open · untriedcode-heavy

Penalty-aware drafts — redundant

Penalty-aligned drafting was added to lift accept, but the reduced-vocab knee already covers the hot penalized tokens. The A/B settled it: at draft_vocab 131072, rep-penalty 1.15, accept holds with it off (0.767 on / 0.776 off), so the per-draft replay is dead overhead — safe to drop. The t/s it saves sits below the cross-process noise floor, so it is cleanup, not a lever.

10 · The instructive part

How we were wrong, and how measurement fixed it

This work moved forward mostly by overturning things I had asserted. The reversals are the most useful thing here, because each one marks a place where a plausible claim survived until a measurement killed it.

asserted · “the metal kernel is the gap”
Measured the stock quantized_matmul scaling: flat to M=4. The verify matmul was already amortized, zero headroom there. The gap was never the kernel.
asserted · “MTP on MoE is a net loss”
Never actually measured when first claimed. When measured, the norm fix had lifted MoE accept to 0.83, and native MoE MTP is net positive.
asserted · “reduced-vocab output is byte-identical”
True only on one easy prompt. Harder prompts diverged on most outputs. The correct claim is quality-neutral, not byte-identical (section 08).
asserted · “frequency-remap beats the free knee”
The first map overfit its own chat corpus and refuted itself on held-out prompts. A broader, held-out map vindicated the mechanism (+7.4 accept points at equal width), but against the banked slice the net was ~1%, inside the noise. Mechanism proven, increment marginal. Kept gated, not shipped.
hoped · “this lever reaches 80”
The confirm run said ~76–77, omlx parity, not 80. Reported the real number, kept the +4 gap open and honest.

The discipline that came out of it: if a mechanism can settle a question, run it before asserting, and label every claim as measured, assumed, or not yet checked. Every number on this page is from a bench run with production down and MLX_ENABLE_TF32=0, or it is cited.
